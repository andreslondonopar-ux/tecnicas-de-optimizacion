Ejercicio 1 — Tiempo de falla de un satélite

“Se tiene un satélite, que para su funcionamiento depende de que al menos 2 paneles solares, de los 5 que tiene disponibles, estén en funcionamiento. Se quiere calcular la vida útil esperada del satélite (MTTF).”

  • Paneles 1 y 2: Normal(media = 50,000 h, desv = 5,000 h)
  • Paneles 3 y 4: Triangular(mín = 30,000 h, máx = 75,000 h, moda = 50,000 h)
  • Panel 5: Normal(media = 55,000 h, desv = 8,000 h)

Planteamiento del modelo

El satélite necesita al menos 2 de 5 paneles funcionando. Si ordenamos las 5 vidas útiles simuladas de menor a mayor \(T_{(1)} \le T_{(2)} \le T_{(3)} \le T_{(4)} \le T_{(5)}\), el satélite sigue operando mientras fallan el 1°, 2° y 3° panel (todavía quedan 2 funcionando). Falla exactamente en el momento \(T_{(4)}\), cuando el cuarto panel se apaga y solo queda 1 (ya no cumple el mínimo de 2). Por lo tanto, la vida útil del satélite en cada simulación es el 4° estadístico de orden (el 2° valor más alto) de las 5 vidas útiles simuladas — la lógica estándar de un sistema de confiabilidad “k-de-n” (aquí, 2-de-5).

simular_satelite <- function(n_sim) {
  panel1 <- rnorm(n_sim, mean = 50000, sd = 5000)
  panel2 <- rnorm(n_sim, mean = 50000, sd = 5000)
  panel3 <- EnvStats::rtri(n_sim, min = 30000, max = 75000, mode = 50000)
  panel4 <- EnvStats::rtri(n_sim, min = 30000, max = 75000, mode = 50000)
  panel5 <- rnorm(n_sim, mean = 55000, sd = 8000)

  paneles <- cbind(panel1, panel2, panel3, panel4, panel5)
  # sort(fila)[4] = 4to estadistico de orden de las 5 vidas de panel
  vida_satelite <- apply(paneles, 1, function(fila) sort(fila)[4])
  return(vida_satelite)
}

Esto confirma que 100 iteraciones ya alcanzan para estimar bien las medidas de tendencia central (media, mediana, cuartiles), tal como se vio en clase.

Donde sí hay una diferencia real es en los percentiles extremos: el percentil 5% (peor caso) pasa de 48062 (n=100) a 48579 (n=1,000) a 48592 horas (n=10,000) — un movimiento de 530 horas entre el extremo y el otro. Esto es exactamente lo que se explicó en clase: pocas iteraciones alcanzan para el promedio, pero hacen falta muchas más para hablar en serio de las colas de la distribución (el peor/mejor escenario).

Ejercicio 2 — Sensibilidad del VPN a la volatilidad del precio

“Considere el caso del ejemplo en caso del proyecto evaluado a partir del VPN. Muestre cómo cambian los resultados de la simulación del VPN si se aumenta la volatilidad del precio de venta del producto de 20 a 35.”

Se usa la misma semilla en ambas corridas — como costos y ventas se generan después de precios en la secuencia de números aleatorios, y cambiar solo el parámetro sd de rnorm() no cambia cuántos números aleatorios consume, ambas corridas usan exactamente los mismos costos/ventas simulados. Así el único factor que cambia es la volatilidad del precio.

simular_vpn <- function(sd_precio, seed = 41677, n_sim = 10000) {
  set.seed(seed)
  inv_inicial <- 200000
  tasa <- 0.10
  tiempo <- 2

  precios <- rnorm(n = n_sim, mean = 200, sd = sd_precio)
  costos <- EnvStats::rtri(n = n_sim, min = 80, max = 130, mode = 100)
  ventas <- rlnorm(n = n_sim, meanlog = log(5000), sdlog = 0.2) %>% round(0)

  utilidad <- (precios - costos) * ventas
  vpn <- (utilidad / (1 + tasa)^tiempo) - inv_inicial
  return(vpn)
}

Respuesta: al subir la desviación estándar del precio de 20 a 35:

  • Probabilidad de éxito (VPN > 0): baja de 97.18% a 89.56% — una caída de 7.62 puntos porcentuales.
  • VPN esperado: prácticamente no cambia ($207,343 → $206,584, una diferencia de solo 0.37%). Esto es esperado: subir la volatilidad del precio no cambia su media (sigue en 200), y la utilidad es lineal en el precio, así que el efecto sobre el VPN esperado es de segundo orden.
  • Dispersión del VPN (desviación estándar): sube de $125,907 a $175,855 — casi se 1.4x su tamaño original.
  • Percentil 5% (peor caso): pasa de $22,803 (positivo) a -$53,847 (negativo) — el peor escenario del proyecto pasa de ser rentable a generar pérdidas.
  • Percentil 95% (mejor caso): sube de $433,151 a $513,330.

En conclusión: aumentar la volatilidad del precio no mueve el resultado esperado, pero sí aumenta fuertemente el riesgo del proyecto — la distribución del VPN se ensancha hacia ambos lados, y el peor escenario pasa de ganancia a pérdida.

Para ambos casos se debe graficar la simulación y se deben de calcular las estadísticas descriptivas y comparar los resultados.”

Se reusa la función simulacion_activo() de Simulaciones.R para la normal, y se crea su equivalente con rtri() para la triangular (usando la media observada como aproximación de la moda, tal como pide el enunciado).

simulacion_activo <- function(valor_inicial, media_rendimiento, sd_rendimiento, periodos){
  activo <- data.frame(periodo = 0:periodos) %>%
    mutate(retorno = c(0, rnorm(n = periodos, mean = media_rendimiento, sd = sd_rendimiento))) %>%
    mutate(rendimiento = 1 + retorno) %>%
    mutate(rend_acum = cumprod(rendimiento)) %>%
    mutate(retorno_acum = rend_acum - 1) %>%
    mutate(capital = valor_inicial * rend_acum, .after = 1)
  return(activo)
}

simulacion_activo_tri <- function(valor_inicial, minimo, maximo, moda, periodos){
  activo <- data.frame(periodo = 0:periodos) %>%
    mutate(retorno = c(0, EnvStats::rtri(n = periodos, min = minimo, max = maximo, mode = moda))) %>%
    mutate(rendimiento = 1 + retorno) %>%
    mutate(rend_acum = cumprod(rendimiento)) %>%
    mutate(retorno_acum = rend_acum - 1) %>%
    mutate(capital = valor_inicial * rend_acum, .after = 1)
  return(activo)
}

Parte 2 — n = 100,000 iteraciones (sin gráfico)

“2. Usando la misma información del punto anterior, se debe de realizar las dos simulaciones. Pero esta vez se debe de realizar n = 100,000 iteraciones en las dos simulaciones (no realices el gráfico de la simulación).”

Nota de implementación: para 100,000 iteraciones se necesita solo el capital final de cada corrida, no la trayectoria mes a mes completa. Probamos primero usar exactamente la misma función simulacion_activo() de la Parte 1 (el mismo estilo purrr::map + dplyr visto en clase) para 100,000 repeticiones, y tardó cerca de 29 minutos solo para la distribución normal (serían ~1 hora para las dos) — computacionalmente inviable para este taller. Por eso aquí se vectoriza el cálculo (una matriz de retornos de 100,000 × 24, con el producto acumulado por fila) en vez de llamar la función 100,000 veces — el resultado matemático es idéntico, solo cambia cómo se calcula.
